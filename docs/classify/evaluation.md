# Evaluation

Training tells you nothing about whether a model is any good. This page is how you find out, and how
to avoid the two ways of fooling yourself.

## The leak that inflates everything

When training data is generated by a rule engine — the whole rule-distillation workflow — every
example of one rule contains that rule's keyword. A random or stratified split puts siblings on both
sides, so the model reads the answer off the training set and the score measures memorisation.

Measured on a reference corpus:

| Split | micro-F1 | macro-F1 |
|---|---|---|
| Random | 0.79 | 0.634 |
| **Grouped** | **0.75** | **0.534** |

The grouped number is the honest one, and the difference is the size of the lie. Grouping costs
nothing when it turns out to be unnecessary, so use it whenever labels came from a generator.

```kotlin
import io.skein.classify.application.GroupedSplitter

val splits = GroupedSplitter().folds(observations = observations, folds = 5)
```

Set `group` to whatever produced the row: the rule, the template, the source document. Rows sharing
a group always land in the same fold.

`GroupedSplitter` is deterministic but deliberately **not** alphabetical. Group names encode
structure, so ordering by name can line a fold up with an entire category — five methods under five
folds put every `one pot` group in one fold, leaving the label that depends on it absent from four
folds' training data. Equal-sized groups are ordered by a seeded mix of the name instead.

## Cross-validation

```kotlin
import io.skein.classify.application.MultiLabelCrossValidator
import io.skein.classify.domain.MultiLabeledText

val report = MultiLabelCrossValidator().crossValidate(
    corpus = corpus.map { row ->
        MultiLabeledText(featureText = row.text, labels = row.labels, group = row.origin)
    },
    vectorizerFactory = { HashingVectorizer(config = hashingConfig) },
    learnerFactory = { LbfgsMultiLabelLearner(featureCount = featureCount) },
    folds = 5,
    threshold = 0.5,
)

report.pooled              // every row, each held out exactly once
report.folds               // per fold — this is what reveals variance
report.meanMacroF1()
report.microF1StandardDeviation()
report.pooledOutcomes      // the raw scores, for sweeps
```

This measures a **recipe** — vectorizer, learner, corpus — not a particular trained artifact.
Running it over the corpus a saved model was trained on says nothing about that model.

**The corpus arrives as text, not features, on purpose.** A vectorizer is built per fold from that
fold's training rows alone. With plain hashing nothing is fitted and nothing can leak, but the moment
an IDF table or a fitted vocabulary enters, building it once over everything moves held-out
statistics into the training features and every score afterwards is wrong in the flattering
direction.

## Metrics

```kotlin
import io.skein.classify.application.MultiLabelEvaluator

val metrics = MultiLabelEvaluator().evaluate(classifier = model, holdout = holdout, threshold = 0.5)

metrics.micro              // precision, recall, F1 pooled over every (record, label) decision
metrics.macro              // the same, averaged per label with equal weight
metrics.exactMatchRatio    // fraction whose predicted set equals the expected set exactly
metrics.coverage           // fraction that received at least one label
metrics.perLabel           // per-label precision, recall, F1, support
```

### Micro against macro

**Micro** pools every label decision before dividing, so frequent labels dominate. It answers "how
often is a label assignment right?".

**Macro** averages per-label figures with equal weight, so a label with four examples counts as much
as one with four hundred. It answers "how well is the model doing across the taxonomy?", and on a
long-tailed corpus it is always the lower and more honest number.

**Watch macro.** Per-label accuracy tracks examples-per-label almost exactly:

| Examples per label | Labels | macro-F1 |
|---|---|---|
| 1–4 | 29 | **0.099** |
| 5–19 | 77 | 0.525 |
| 20–99 | 103 | 0.595 |
| 100+ | 28 | **0.784** |

That relationship transfers even when the absolute numbers do not. It is also the argument for a
hybrid: keeping rules for the sparse tail is a design, not a compromise.

Macro averages over **every** label that was expected or predicted, including labels the model
invented. A hallucinated label drags it down, which is stricter than the common convention of
averaging only over labels with support.

### Coverage

The column most often omitted and the one that makes the trade legible. A threshold with excellent
precision that labels a third of your records is a different product from one that labels all of
them, and precision alone hides the difference.

## Threshold sweeps

```kotlin
MultiLabelEvaluator().sweep(outcomes = report.pooledOutcomes).forEach { point ->
    println("${point.threshold}  P ${point.precision}  R ${point.recall}  covered ${point.coverage}")
}
```

A typical shape:

| threshold | precision | recall | F1 | with ≥1 label |
|---|---|---|---|---|
| 0.20 | 0.896 | 0.614 | 0.729 | 75.9% |
| 0.50 | 0.970 | 0.501 | 0.661 | 63.0% |
| 0.80 | 0.989 | 0.348 | 0.515 | 46.5% |

**There is no correct row.** Accepting more labels always trades precision for recall, and which
side is right depends on what a wrong label costs against what a missing one costs. The library will
not choose for you.

The sweep re-reads scores already computed, so a hundred thresholds cost no more model evaluations
than one.

## Ranked recall

```kotlin
MultiLabelEvaluator().recallAtK(outcomes = report.pooledOutcomes)   // {1=…, 2=…, 3=…, 5=…}
```

Ignores the threshold entirely and answers: would a reviewer shown *k* candidates find the right
label? Measured on a reference corpus, `recall@1 = 0.484` against `recall@3 = 0.775` — if a person
is in the loop, this is usually the number that matters.

## Single-label evaluation

```kotlin
import io.skein.classify.application.ModelEvaluator

val report = ModelEvaluator().crossValidate(
    observations = observations,
    classifierFactory = { NaiveBayesClassifier() },
    folds = 5,
)

report.pooled.accuracy
report.pooled.macroAverage
report.pooled.confusionMatrix
report.pooled.expectedCalibrationError
```

Conventions worth knowing:

- For single-label multi-class problems, micro precision, recall and F1 all provably equal accuracy.
- `logLoss` clamps the true label's probability at `1e-15`, so an unseen label yields a large but
  finite penalty.
- `expectedCalibrationError` is the support-weighted gap between confidence and accuracy. Expect a
  poor value from Naive Bayes even at high accuracy — that is what
  [calibration](single-label.md#calibration-and-abstention) exists to correct.

## Keep a hand-labelled held-out set

If your labels came from rules, everything above measures how well the model reproduces the rules.
That is worth knowing and it is not the question you actually have.

Keep a separate set, labelled by a person, using wording the rules do not cover. It will score
worse. That gap is the finding — it is the only measurement that answers whether the model
generalises past the rules, and an evaluation that omits it teaches the wrong lesson.

The [recipe example](../../examples) prints both numbers side by side and says which is which.
